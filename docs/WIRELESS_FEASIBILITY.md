# MX9A0 无线 CarPlay：调查已停止

**2026-10-11 状态：车主决定停止无线调查，仅保留 0.34 有线版。当前车机环境下没有实现无线 CarPlay，本项目不提供无线支持。原厂蓝牙可打电话不等于向 Android 应用提供了可用的 iAP2/RFCOMM 通路；缺少模块完整规格和固件证据，不能把未实现写成硬件绝对无法实现。2.4GHz 的担忧也不能单独作为硬件不可能的证明。**

以下为历史调查记录。2026-10-10 开始在冻结 0.34 有线基线之外推进无线调查。**目前既没有证明无线可用，也没有足够证据证明硬件绝对不支持。0.36 是无线信息检测版，不是已实现无线连接的版本。**

## 已确认的信息

- 该车原厂蓝牙音乐和电话可用，但此前标准 Android `BluetoothAdapter` 检测为关闭，系统也未声明标准蓝牙 feature。这只能说明标准接口没有反映原厂蓝牙能力，不能推断没有蓝牙硬件。
- 本地原车软件分析显示，`com.byd.btservice` 的上层 SPP 接口传递 `String`，收取的数据还经过默认字符集转换。它不能直接充当任意二进制 iAP2 流的可靠传输层。
- 更底层的 `com.byd.btserialservice` 暴露 `IBtSerialService.sendBtCMD(byte[])`，接收侧通过 `INTENT_SERIAL_BT_DATA` 广播字节数组。服务访问 `/dev/btdevice`，是厂商模块命令链路，不是已证明可用的 Android RFCOMM socket。
- 已检查的串口服务对命令有自己的消息头约束。当前接口中未发现可直接指定 iAP2 服务 UUID 的参数；能写字节数组并不证明模块支持 iAP2、可选服务 UUID 或任意蓝牙协议。
- DiPlay 上游无线启动流程通过蓝牙 iAP2 认证、Wi-Fi 信息交换再进入网络投屏；旧系统还需核实热点、网络接口和服务发现能力。

原车 APK 和反编译文件仅用于本地分析，不随公共仓库发布。

## 为什么还要检查 Wi-Fi

Apple 的 [无线 CarPlay 系统说明](https://developer.apple.com/videos/play/wwdc2017/717/) 描述了蓝牙发现/重连、iAP2 服务以及 Wi-Fi 音视频传输的分工，并说明热点广播信息元素的要求。蓝牙电话或音乐正常，并不证明无线 CarPlay 所需的发现与数据通道可用；仅连接同一个 Wi-Fi 也不能直接代替这些握手。

USB 首次配对有助于建立无线关联，但不能据此认定后续重连完全不需要可用的蓝牙能力。上述官方设计要求与本项目的实际互通试验必须分开，不把某一个标志或接口存在当作认证/兼容性证明。

## 0.36 的按需检测

现有「环境检测并提交」新增 `wirelessReadiness`，不额外增加主界面按钮：

- 标准蓝牙状态与已配对数量，不记录手机名称或地址。
- 原车蓝牙/串口服务版本、导出与权限信息、接口方法签名（不调用这些业务方法）。
- 尝试绑定**已经运行**的厂商串口服务，最多等待 1.5 秒，不自动启动服务、不发送 Binder 命令，完成后解除绑定。
- 被动观察最多 2 秒蓝牙串口广播，仅保存次数/长度和可能出现的模块版本数值，不保存原始字节或通讯录。广播不是经认证的来源，未收到广播也不能判定模块不存在。
- Wi-Fi 状态、现有热点接口、缓存扫描频段统计、网络接口 IPv4/IPv6 数量以及可读取的驱动信息。不读取热点密码，不记录 SSID、BSSID 或 IP 地址。
- `/dev/btdevice` 等节点的可见性/权限，只查看文件属性，不打开设备。

不自动开启标准蓝牙、不配对、不启动扫描、不改热点、不改变音频路由。API存在、权限可读、缓存中有5GHz信号都不等于已验证热点或CarPlay通道。

## 历史测试计划（已停止，不再执行）

停车后在线更新到 0.36，保持原车蓝牙已连接 iPhone，点一次「环境检测并提交」。不需要断开原车蓝牙或反复寻找标准蓝牙设置。若方便，可再在未插 USB、原车蓝牙仍连接手机的状态提交一份；这是区分 USB 与原厂蓝牙环境的补充，不要求重新配对。

依结果决定下一步：标准 RFCOMM 路径、已确认协议下的厂商模块适配，或明确报告软件层面的不可行边界。若模块固件不支持所需服务且无可用扩展接口，不能用“获取 root”来代替硬件/固件能力。当前尚未取得足以做出该最终结论的模块资料。

每个实验版仍配套相同安装编号的 0.34 稳定回退包；需要日常用车时恢复有线稳定版即可。
